# Gyro 识图时临时借用显存

2026-11-23。方案以 Strata 0.2.19 / Engine 0.1.65 的 `c6f6427d9de9016fd92d13e29740f65625261df7` 为基础，面向 RTX 3080 12 GiB、32 GB DDR5、Gyro-S、单请求 `/v1/chat/completions`。已实现为独立 opt-in [vision-expert-lease 功能包](../features/vision-expert-lease/README.md)，已完成 SM86 构建、真实 GPU 映射测试及真实图片 API 检查。完整驻留、256K 无头验收尚未执行；桌面受限预算结果不能替代它。

## 目标和生命周期

平时视觉编码器保留在磁盘，专家缓存使用日常显存预算。同一图片的编码结果可继续使用上游磁盘缓存。

一次有新图片的请求依次执行以下步骤。

1. 服务在现有请求 FIFO 中取得图像编码的执行时段。引擎排空 verify、专家自适应交换、异步复制和预填充借槽。
2. 记录日常缓存容量、即将让出的槽位及其 `(layer, expert)`、当前专家驻留表和归还所需的数据来源。借出期间保持这些专家的归属稳定。
3. 按视觉编码器在当前图片 token 上限下的实际预算，释放完整显存段。编码器使用这部分显存完成本次全部图片编码。
4. 图像 embedding 交给上游既有磁盘缓存。结束编码器进程，并确认其显存已归还。
5. 将原显存段映射回原虚拟地址，恢复原来的专家及驻留表，等待复制完成后确认缓存归还。
6. 语言模型读取图片 embedding 和文本，开始预填充及生成回答。再次提交已编码的图片可以直接命中图片缓存。

编码器在完成图片编码后就能退出。上游 `Vision.unload()` 保留磁盘中的编码结果，因此语言模型回答时不需要视觉权重继续占用显存。

## 复用的上游能力

- `terminal/serve/server.py` 中的 `Vision`、`Service._vision_up()`、`_vision_idle_down()`、图像缓存和 FIFO。
- `engine/src/core/expert_cache.cpp` 的分段显存及稳定虚拟地址。
- `engine/src/program/generate.cpp` 的显存请求安全点、驱逐列表、缓存回填和驻留表上传。
- `FileExpertSource` 的既有专家读取及布局转换能力。

新增一个专用于图像编码的借还事务，由现有服务和引擎控制路径承接。可让出的容量由本次编码预算决定。编码结束即归还的行为需要显式接线，上游默认是闲置约 120 秒后退出编码器。

## 32 GB 内存下的数据去向

当前低内存模式只在 RAM 保留 GPU 缓存的专家补集。GPU 上的一些专家只有 GPU 副本，因此原有 `VRAM` 命令会拒绝伸缩。这是本方案必须解决的核心关系。

语言模型在图像编码期间暂停，让出的 GPU 专家可以暂时只保留原始模型文件中的数据和槽位记录。归还时复用 `FileExpertSource`，以少量有上限的暂存缓冲逐个恢复缓存所需的专家布局。RAM 中原有的专家补集继续保留。读取与异步上传完成之前，暂存缓冲必须保持有效。

首版先保证同槽、同专家、同数据恢复。恢复结束后，正常解码继续具备原来的 GPU+RAM 专家覆盖。暂时读盘的代价集中在图像编码前后的交接阶段。恢复时间包含磁盘读取、必要的布局处理和 PCIe 上传，实际延迟需测量。

## 首版实现范围

新方案围绕一个视觉借还补丁实现以下关系。

- 单 GPU、单语言请求、Gyro-S 低内存驻留模式。
- 请求图像编码前借出，在同一次请求开始语言推理前归还。
- 借还过程保存专家归属、映射容量与日常 reserve。
- 在借出前确认所有读者和预填充借槽已经排空。
- 所有图片成功、编码失败和客户端取消都进入归还路径。
- 恢复期间先完成数据上传，再发布专家驻留。GPU 段无法完整映射或回填失败时，当前请求给出清楚的错误，由显式的恢复流程处理模型状态。

首版使用现有图片预算计算，包含权重、图片 token 上限对应的工作区及余量。本机设128MiB显存分段减少舍入浪费，尚未做128/512MiB吞吐对比；图片预算1024 token已通过真实API检查。

日常保留 Gyro-S、DFlash2、prior 0.5 和成对行。量化和路由设置在借还前后相同，便于验证同一输入的数值与缓存恢复。

## 实现和验收顺序

先完成纯引擎的借出与归还，以合成专家验证段映射、槽位、数据校验和失败回滚。接着接入真实 `/v1/chat/completions` 图片编码生命周期，再在无头环境完成模型验收。

每轮记录编码器启动前后的显存、最低可用 RAM、交换空间变化、让出的专家数量、模型文件读取量、缓存恢复耗时和恢复后生成时的专家文件读取量。分别测首次图片、同图缓存、多图、连续识图、取消与编码失败。

验收须同时满足正常回答、编码器退出、缓存归还与恢复后解码不依赖专家文件读取。纯 VMM 测试通过只证明底层分段操作，真实图片请求才能证明完整交接流程。

## 当前实现和验收状态

活动栈已经加入 `vision-expert-lease`。原有普通 VRAM 命令的 complement resident 拒绝条件保留；新增专用 `VISION_LEASE BEGIN/END`，借出时冻结所有权并禁止语言模型工作，完整恢复后才解除门禁。部分失败保留事务，允许重试归还。

C++/GPU测试3项、视觉与手动入口Python测试64项、既有控制回归25项通过。真实API检查覆盖冷图、缓存、多图、借出后取消、坏图400、编码器启动失败503及后续文本；1024 token图片预算另做4项检查。测试图均自行生成。实际恢复暂存1049600 bytes；专家归还约1.3–1.9秒。完整数据、早期失败和环境见 [验收记录](../features/vision-expert-lease/validation/README.md)。

本机下一次无头启动启用该功能，正常启动不发送测试prompt。显式运行 `sudo ~/.local/bin/strata-headless-compare --vision-check` 才执行完整驻留检查、冷图/缓存图和恢复后的3072-token输出；要求生成阶段零专家文件blob读取。桌面active时该命令拒绝运行，不自动切换桌面或网络。

旧PR5500 V2/V3完整存档、BF16 PLE、SM86分派与宽lookup均保留。Live Memory、Runtime KV Storage、Shutdown Persistent Cache仍为reference，未启用。
